## 1. Что это

Последние три временных слота каждого дня в календаре планирования свидания
запираются: на них плашка **Premium** и замок. Открыть их можно двумя способами —
активной подпиской Gennety Premium у **любого** из пары, либо разовой покупкой за
Telegram Stars, открывающей полосу **на это конкретное свидание**.

Экран Premium получает соответствующий пункт преимуществ: подписчику доступны все
времена, всегда.

## 2. Механика, которая диктует весь дизайн

`processCalendarSlotsUpdate` (`handlers/matching/scheduler.ts`) фиксирует время,
когда пересечение множеств `availableTimesA` и `availableTimesB` равно **ровно
одному** слоту. Отсюда следует то, что нельзя обойти:

> **Разблокировка — свойство МАТЧА, а не пользователя.**

Если бы пропуск открывал полосу только купившему, он бы не покупал ничего: тот
отметил 19:30, партнёр отметить не может, пересечение никогда не содержит 19:30,
свидание на 19:30 не фиксируется. Одна оплата (или одна подписка) открывает полосу
обеим сторонам.

Побочный, но приятный эффект: покупка читается как жест в сторону партнёра — та же
природа, что у «оплатить билет за двоих» (§3.5b), и её можно так и подать.

Прецедент в коде уже есть: `pairPremiumActive` в
`handlers/matching/venue-change.ts:316` — премиальные заведения на доске смены
места открыты паре, если подписка есть **у любого** участника. Здесь та же форма.

## 3. Полоса: какие именно слоты

`CALENDAR_TIME_SLOTS` — константа из 14 записей (13:00…19:30 через 30 минут).
Полоса выводится из неё:

```ts
export const PRIME_TIME_SLOTS = CALENDAR_TIME_SLOTS.slice(-PRIME_TIME_SLOT_COUNT);
```

Два правила, оба несущие:

- **Второго списка часов не существует.** Захардкоженный `[18.5, 19, 19.5]`
  разъедется с сеткой при первой же её правке, и разъедется молча — сервер
  запретит слот, который клиент рисует свободным. Тот же принцип, по которому
  `MIN_PHOTOS` живёт в одном месте.
- **Предикат считает по киевским настенным часам**, а не по UTC. Дроплет работает
  в UTC; `generateProposalSlots` документирует ровно эту ловушку («bare
  `setHours(13)` would write 13:00 UTC ≈ 16:00 Kyiv»). `isPrimeTimeSlot(date)`
  читает час/минуту через `zonedParts(date, CALENDAR_TIME_ZONE)`, поэтому он
  корректен и через переход на зимнее время.

При `PRIME_TIME_SLOT_COUNT = 3` запертыми становятся **18 из 84** ячеек (21%).

## 4. Кто открыт

Чистая функция `primeTimeUnlocked(match, now)` → `true`, если верно **любое**:

1. `PRIME_TIME_ENABLED` выключен — фича инертна, ничего не заперто;
2. `PREMIUM_FEATURE_ENABLED` выключен — альтернативный путь нельзя купить, значит
   запирать нечестно;
3. у любого участника активна подписка (`isPremiumHeadActive`, зеркало
   `pairPremiumActive`);
4. `match.primeTimeUnlockedAt != null` — разовый пропуск оплачен;
5. **grandfather:** любая сторона уже отметила слот из полосы (см. §13.1);
6. **ни одна** из сторон не может дотянуться до покупки (§12) — fail-open.

## 5. Цена

`PRIME_TIME_STARS` — **50**. В интерфейсе показываются **только звёзды**; строки
с долларами у этой фичи не существует.

Это решение про честность, а не про оформление. deploy.md держит жёсткое правило:
подпись не имеет права быть **дешевле** звёзд, которые реально списываются («a
label cheaper than the Stars it spends is the one kind of wrong price that takes
money from a user who was told otherwise»). По двум задокументированным курсам
50⭐ стоят пользователю $1.00 (тикетный, $0.02/⭐) и ~$1.20 (премиальный,
$0.024/⭐) — то есть подпись «$0.99» под-обещала бы при обоих. Показывая только
звёзды, мы не делаем утверждения, которое может оказаться ложным: реальную сумму
Telegram называет сам в платёжном листе.

Побочно 50⭐ — ровно один минимальный пакет звёзд, то есть психологически
правильный размер покупки.

**Env `PRIME_TIME_PRICE_USD_DISPLAY` не заводится.** Переменная, которую никто не
рендерит, — это будущее расхождение с ценой.

## 6. Точка принуждения — одна

Обе поверхности календаря (Mini App через `initData` и нативная
`/v1/matches/:id/calendar`) уже сходятся в **двух** функциях
`handlers/matching/scheduler.ts`, обе ключуются по `telegramId`
(`calendar-native.ts` резолвит его из JWT). Значит проверка ставится один раз и
достаётся обеим:

```ts
// processCalendarSlotsUpdate, рядом с существующей проверкой allowlist
if (!unlocked && picks.some(isPrimeTimeSlot)) {
  return { ok: false, reason: "prime-time-locked" };
}
```

Путь подтверждения при нескольких пересечениях (`overlapCandidates` → повторный
POST одним iso) идёт через ту же функцию и наследует проверку бесплатно.

`getCalendarState` дополняется блоком `primeTime` (заперто ли, какие слоты, цена,
открыла бы подписка) — читают его Mini App и ничего больше (см. §12).

Новый отказ `prime-time-locked` → **HTTP 402** на обоих маршрутах, зеркаля
`premium-locked` доски смены места.

## 7. Поверхности

**Mini App календаря** (`apps/webapp/src/main.ts`):

- `paintSlotState` получает состояние `locked`: приглушённая ячейка, замок,
  маленькая плашка «Premium» — форма уже отработана на карточках премиальных
  заведений.
- Тап по запертому слоту **не переключает** его, а открывает шторку с двумя
  ступенями: герой «Открыть вечер — 50 ⭐» (`WebApp.openInvoice`) и тихая вторая
  «Gennety Premium — все времена, всегда» (переход на `premium.html` через
  существующий `return-to.ts`, который уже умеет возвращать назад по цепочке).
  Ровно одна громкая кнопка на экран — правило §3.5b.
- После успешной оплаты — перечитать состояние; партнёру полоса откроется на его
  собственном опросе (~4 с).

**Бот:** короткий DM партнёру, что полоса открыта, по образцу
`ticketPeerTookTheirs`. Без него сетка у него меняется молча под пальцем.

## 8. Схема

Аддитивно на `matches`:

- `prime_time_unlocked_at DateTime?`
- `prime_time_paid_by_id String? @db.Uuid` — кто заплатил (null, если открыла
  подписка).

Новая таблица `prime_time_purchases` — копия `venue_change_purchases`: `userId`,
свободный `matchId` (без FK, чтобы удаление матча не рвало платёжный след),
`status` (`processing` → `settled` | `refunded_race` | `refunded_stale` |
`refunded_match_died` | `refund_failed`), уникальный `externalPaymentId`,
`amountStars`, `resolvedAt`, `refundError`. Плюс ежечасный свип-возврат — копия
`services/venue-change-refund.ts`.

`refunded_match_died` — следствие решения №3 (§9.1). Он же делает таблицу
обязательной, а не желательной: возврат при смерти матча — это провайдерский
вызов, который падает, и без durable-строки упавший возврат не с чем сверить.

**Альтернатива, названная честно:** строка с нулевой дельтой в `ticket_ledger` с
новой причиной (`reason` — обычный `String`, миграции не требует) дала бы
exactly-once, ленту фаундера и админский реестр выручки бесплатно, без таблицы и
без крона. Прецедент есть — `premium_gate`. Против неё то, что ARCHITECTURE прямо
формулирует правило: разовая покупка идёт по образцу `rematch_purchases`, а не
кошелька. Рекомендую таблицу; цена рекомендации — пятый источник в
`services/purchases.ts` плюс лента фаундера, админский реестр и раздел
монетизации.

## 9. Платёжная рельса

Payload `prime:<matchId>` (зеркало `venue:<matchId>:<mode>`).

- `pre_checkout_query` — перепроверить форму payload, сумму звёзд, что матч всё
  ещё `negotiating` и полоса всё ещё заперта (ссылки на инвойс переиспользуемы).
- `successful_payment` — порядок в точности как у Rematch, и он же гарантия
  «деньги либо что-то меняют, либо возвращаются»:
  1. **сначала** строка покупки по уникальному charge id (`P2002` = повторная
     доставка → идемпотентный no-op);
  2. CAS разблокировки (`updateMany … where primeTimeUnlockedAt IS NULL`);
  3. исход: `settled` — либо возврат и `refunded_race`, если CAS не выиграл
     (обе стороны оплатили одновременно). Неудавшийся возврат паркуется в
     `refund_failed` и **никогда** не объявляется пользователю выполненным.
- Инвойс минтится `POST /v1/calendar/prime-time/stars-invoice` (`initData`),
  404 при выключенном флаге.

### 9.1 Возврат при смерти матча

Решение №3: свидание не состоялось → пропуск возвращается. Рельса — та же, по
которой уже возвращается Date Ticket (§3.5b): шесть путей смерти живого матча
(заморозка, GDPR-удаление, три ветки модерации, экстренная отмена и 48-часовая
цепочка §3.5c) сходятся в одном планировщике, и он получает вторую половину.

Четыре правила, каждое из которых легко нарушить:

- **Возвращаем ЗВЁЗДЫ, а не билет.** §3.5b кладёт возврат в кошелёк билетов
  сознательно — там реверс Stars был бы провайдерским вызовом без своей таблицы.
  Здесь таблица есть (§8), а смешивать валюты нельзя: человек заплатил 50⭐, и
  вернуть ему билет за $6.99 — абсурдная щедрость, а вернуть «часть билета»
  невыразимо.
- **Возвращаем тому, кто платил** (`primeTimePaidById`), и только строкам в
  статусе `settled`. Полоса, открытая подпиской, ничего не стоила — возвращать
  нечего.
- **Отменивший возвращает так же, как тот, кого отменили.** Правило §3.5b
  дословно: наказание за срыв уже живёт в Elo и `silentIgnoreCount`, и брать
  деньги сверху значит делать честную отмену дороже молчаливого неявления.
- **Возвращаем независимо от того, зафиксировала ли пара слот из полосы.** Если
  они договорились на 19:30 и матч потом умер — свидание всё равно не состоялось.

Идемпотентность — уникальный `externalPaymentId` строки покупки плюс CAS по
`status = 'settled'`; повторный прогон рельсы (шесть путей, ретраи свипа) не может
вернуть дважды.

## 11. Демо-режим

Два факта, каждый ломает демо, если его не учесть.

**Кукла контрит именно в запертую полосу.** `DEMO_COUNTER_TARGET_HOURS = [18, 19,
17]` (`demo/decide.ts:642`) — партнёр предлагает 19:00, а это середина полосы. То
есть визитёру предложат время, которое он не может отметить, и демо упрётся в
календарь.

**Мок-рельсы для звёзд в демо нет вовсе** — смена места там settle-ится
бесплатно (`changeIsFree`).

Рекомендация, зеркалящая `changeIsFree`: **показывать замок и открывать полосу
бесплатно** одной охраняемой веткой. Инвестор видит монетизацию — ради чего её и
показывают — и проходит дальше.

**Чего делать нельзя:** двигать `DEMO_COUNTER_TARGET_HOURS`, чтобы кукла обходила
полосу. Это отменило бы решение 2026-08-17 и вернуло бы предложения на середину
рабочего дня.

## 12. iOS и правило двух клиентов

**Решение фаундера: гейтим всех одинаково.** Я рекомендовал обратное и был не
прав в оценке цены — §2 уже делает эту цену почти нулевой, и вот почему.

Разблокировка — свойство **матча**, а не пользователя. Значит в смешанной паре
(Telegram + iOS) телеграмная сторона покупает пропуск или несёт подписку, и
полоса открывается **обоим**. Нативный пользователь не в тупике: у него есть путь,
просто путь идёт через партнёра. Это ровно та же форма, что «оплатить билет за
двоих» — один платит, оба идут на свидание.

Настоящий тупик остаётся ровно один: пара, где **обе** стороны недостижимы в
Telegram. У неё нет ни Stars-рельсы, ни покупаемого Premium (группа подписок ни
разу не отправлялась на ревью — deploy.md), то есть три запертых слота без
единого способа их открыть. Такая пара **не запирается вовсе** — предикат
`primeTimeUnlocked` возвращает `true`, когда `telegramReachable` ложно для обеих
сторон. Сегодня это состояние в проде недостижимо (нативных пользователей нет), и
предикат существует затем, чтобы оно не стало достижимым молча.

**Что решение №4 обязывает нас сделать позже:** дать iOS собственный путь покупки
— StoreKit-консьюмабл `prime_time_pass`, по образцу уже существующих
`APPSTORE_TICKET_PRODUCTS`. Это отдельный слайс (M7), отложенный до выхода
приложения; до него iOS-сторона зависит от партнёра, что честно и работает.

**Контракт `/v1/*` меняется.** Нативный календарь теперь гейтится, значит
`GET /v1/matches/:id/calendar` обязан нести блок `primeTime` (что заперто и
почему), иначе клиент рисует свободными ячейки, которые сервер отвергнет с 402.
Это аддитивная правка `openapi/gennety-v1.yaml` в том же коммите и задача в
`~/Desktop/Gennety-iOS/IMPLEMENTATION_PLAN.md`.

Ловушка контракта, на которой этот репозиторий обжигался трижды: **никаких
`oneOf: [$ref, "null"]`** — swift-openapi-generator молча выбрасывает такую форму,
и поле просто не доедет до клиента. Отсутствие значения выражается отсутствием
свойства (DECISIONS 2026-08-10). Гейт контрактного изменения — прогон
`./scripts/generate-api.sh` с нулём строк `Schema "null" is not supported`, а не
`openapi:lint`.

## 13. Крайние случаи

1. **Матчи в полёте.** Запереть полосу задним числом — значит отобрать у пары
   слот, который она уже отметила. Правило: если любая сторона уже держит слот из
   полосы, матч считается открытым. Само-исцеляется, миграции не требует. (В
   проде живых `negotiating` практически нет, так что цена нулевая в любом случае.)
2. **Подписка, истёкшая посреди переговоров.** `pairPremiumActive` вычисляется
   живьём, поэтому истёкшая подписка вернула бы замок на слоты, которые пара уже
   выбрала. Правило: **первая же отметка слота из полосы под активной подпиской
   ставит `primeTimeUnlockedAt`**, превращая живое право в постоянное свойство
   матча. Та же логика, по которой §3.5b объявляет закрытый слот билета
   необратимым.
3. **Обе стороны платят одновременно** → второй заряд возвращается
   (`refunded_race`).
4. **Premium куплен после пропуска** — сверять нечего, пропуск потрачен.
5. **Свидание не состоялось** — звёзды возвращаются (§9.1). Следствие для копии
   оффера: она **не** говорит «возврата нет» и **не** обещает возврат громко —
   обещание, вынесенное на кнопку покупки, продаёт отмену вместо свидания.
6. **Подписка у одного, пропуск куплен другим.** Порядок безразличен: полоса уже
   открыта первым событием, второе — no-op. Но если пропуск успел оплатиться
   ДО того, как подписка была замечена, деньги списаны честно и возвращаются
   только по §9.1; «у партнёра же есть Premium» задним числом не отменяет покупку,
   которая в свой момент была единственным путём.
7. **Слепое решение, отсутствие чата, единственный живой матч** — не затронуты.

чем замок, но не хуже, чем клиент, гейтящийся по полю, которого сервер ещё не
шлёт).

## 16. Гварды

Каждый подтверждается **красным** до фикса:

- полоса выводится из `CALENDAR_TIME_SLOTS`, считается по Киеву, переживает DST;
- снятие проверки в `processCalendarSlotsUpdate` роняет тест;
- оплата одной стороной открывает полосу **обеим**;
- отметка под подпиской штампует `primeTimeUnlockedAt` (истечение подписки полосу
  не возвращает);
- второй заряд возвращается;
- пара, где обе стороны недостижимы в Telegram, не запирается (fail-open);
- смешанная пара: оплата телеграмной стороной открывает полосу и на нативном маршруте;
- смерть матча возвращает звёзды ровно один раз на шести путях §3.5b, и ничего не возвращает, если полосу открыла подписка;
- генератор Swift-клиента не выбрасывает новое поле (ноль строк `Schema "null" is not supported`);
- контр-предложение куклы (19:00) в демо достижимо.

## 17. Принятые риски

- **Это вторая плата в одном флоу** — после Date Ticket за само свидание.
- **Заперта именно желанная полоса.** Лист времени открывается на 19:30 ровно
  потому, что «вечер — это тот ответ, который обычно и нужен» (решение
  2026-08-08). В этом и монетизационный тезис, и риск.
- **Сетку расширили до 13:00 в 2026-07 специально ради дневных свиданий.**
  Запирая 18:30+, мы возвращаем неплатящих в 13:00–18:00, что для работающего
  человека почти неприменимо.
- **Меньше поверхности пересечения → чаще состояние «оба выбрали, ничего не
  совпало»** (§3.6b, статус там намеренно не показывается) → чаще отмена по
  48-часовой цепочке §3.5c. За этой метрикой надо следить после флипа: доля
  no-overlap, доля отмен, конверсия в разблокировку.

## 18. Сознательно не делаем

- Путь покупки на iOS **в v1** — это M7, после выхода приложения.
- Разблокировку на пользователя вместо пары — механика её запрещает (§2).
- Любые изменения самой сетки слотов.
