## Две поправки к прежним вводным

**1. `telegramId < 0` — НЕ признак тестового аккаунта.** Отрицательный
`telegramId` означает **мобильную рельсу**: так устроены все аккаунты, не
пришедшие через Telegram-бота (ARCHITECTURE → `users`). Сегодня отрицательных
31: 30 синтетических профилей и один настоящий аккаунт фаундера. В день выхода
iOS этот фильтр начнёт выбрасывать каждого реального пользователя приложения.

Правильный признак сервер считает сам и отдаёт готовым. Никогда не выводи его
из id:

- пользователь тестовый ⇔ `health.classification === "test"` в `/admin/users`;
- матч не считается ⇔ `source === "synthetic"` **или** в паре есть тестовый.

Все знаменатели в `/admin/stats`, `/admin/dashboard` и
`/admin/analytics/monetization` уже посчитаны по этому правилу. Пересчитывать
их самостоятельно из `users.total` не нужно и вредно.

**2. Платёжные эндпоинты СУЩЕСТВУЮТ.** В прежних вводных было сказано, что их
нет. Есть два, и оба отвечают:

- **`GET /admin/purchases`** — леджер всех денежных движений: фильтры `kind`,
  `status`, `userId`, `since`, `until`, пагинация, плюс `totals` и `byKind` по
  ВСЕЙ отфильтрованной выборке, а не по странице. Намеренно без кэша.
- **`GET /admin/analytics/monetization`** — конверсия в платящих с **тремя**
  знаменателями (все реальные регистрации / активированные / дошедшие до
  платного экрана), выручка, ARPU/ARPPU, когорты, разрезы по каналу, полу,
  городу и треку, повторные покупки, время до первой оплаты. Кэш 15 мин,
  `?fresh=1` обходит, заголовки `X-Data-Generated-At` / `X-Data-Cache`.

Эндпоинтов `/admin/tickets`, `/admin/payments`, `/admin/refunds` действительно
нет — их роль выполняют эти два.

## Что появилось: `matches.conversion` в `/admin/stats`

```jsonc
"conversion": {
  "confirmed": 0,              // знаменатель: оба сказали «да»
  "ticketsPurchased": 0,       // числитель до вычетов: ОБА билета оплачены
  "ticketsPartial": 0,         // один билет из двух — ещё не свидание
  "noShow": 0,
  "ghostDuringScheduling": 0,
  "refunded": 0,
  "deductions": 0,             // объединение трёх выше ∩ оплаченные
  "netPct": null,              // ГЛАВНОЕ ЧИСЛО
  "grossPct": null,            // без вычетов
  "noShowRateOfPaidPct": null, // качество планирования
  "ghostRateOfPaidPct": null,
  "excludedSynthetic": 13,
  "excludedTest": 1
}
```

### Формула, и чем она отличается от буквальной

```
netPct = (ticketsPurchased − deductions) / confirmed × 100
```

- **Знаменатель — подтверждённые матчи** (`acceptedByA && acceptedByB`), без
  синтетических и без тестовых пар. `proposed` и истёкшие без ответа не входят.
- **«Билет куплен» = ОБА слота.** §3.5b — жёсткий гейт: календарь не
  открывается, пока не оплачены оба, так что один билет свиданием не
  становится. `ticketsPartial` отдаётся отдельно и не приравнивается ни к 0,
  ни к 1.
- **Вычеты — ОБЪЕДИНЕНИЕ, а не сумма.** Исходная формула
  `куплено − (no_show + ghosting + возвраты)` считает один испорченный матч
  дважды или трижды: no-show и гостинг как раз и порождают возврат. Каждый матч
  вычитается один раз; компоненты в ответе — чтобы показывать их рядом, а не
  чтобы складывать.
- **Вычитается только то, что было в числителе.** Матч без оплаченных билетов,
  закончившийся гостингом, — не «минус продажа», а просто не продажа.

### Правило нулей — самое важное для интерпретации

**`null` ≠ `0%`.** `null` означает «нет данных» (пустой знаменатель или
знаменатель без продаж) и должен рендериться как «нет данных». Ноль означает
измеренный ноль. Путать их нельзя: сегодня `netPct: null`, и это НЕ «конверсия
ноль процентов» — это «ни одна реальная пара ещё не дошла до подтверждённого
матча».

### Что показывают эти числа сегодня (замер 2026-08-15)

`confirmed: 0` при 14 матчах в базе. Причина: 13 синтетических (партнёр-заглушка
по построению всегда отказывает, купить билет не может) и 1 тестовая пара —
единственный `completed` матч в истории прода оказался засеянной строкой с
синтетическим участником. **Органических свиданий в проде не было ни одного,
покупок — ноль.** Поэтому раздел будет пустым, пока не появятся продажи; это
ожидаемое состояние, а не поломка. Не пиши «конверсия упала» — писать нечего.

## Что появилось: `derived` в `/admin/dashboard`

```jsonc
"derived": {
  "weeklyPaidDates": 0,                 // North Star
  "matchToTicketConversionPct": null,   // = conversion.netPct
  "matchToTicketGrossPct": null,
  "matchNoShowRatePct": null,
  "matchGhostRatePct": null,
  "registeredToMatchRate7dPct": 0,
  "registeredReal7d": 4,
  "matchedLast7Days": 0,
  "cacPerPayingUsdCents": null,
  "cacPerActiveUsdCents": null,
  "ltvCac": null,
  "roas": null
}
```

- **`weeklyPaidDates` считается по МАТЧАМ, не по плательщикам.** Мужчина,
  оплативший за двоих, — это одно свидание и один плательщик, а не два. И это
  не выводится из `purchaseSummary.count`: тот пожизненный и на вопрос «за 7
  дней» ответить не может в принципе. Момент продажи — когда закрылся ВТОРОЙ
  слот.
- **`registeredToMatchRate7dPct`, а не «install→match».** Установок продукт не
  трекает вовсе: iOS ещё не вышел, а канал (`referralSource`) фиксируется уже
  на регистрации. Метрика называет то, что измеряет; «install» здесь был бы
  одной метрикой под именем другой. Если в задании написано «Install→Match
  Rate» — это оно.
- **`cacPerPaying` / `ltvCac` / `roas` — всегда `null` и это не баг.** Данных о
  расходах на привлечение в продукте нет вообще (нет интеграции с рекламными
  кабинетами, нет ручного ввода). Дизайн механизма ввода — в
  `AD_SPEND_TRACKING_DESIGN.md`, реализация не начата. **Показывай «нет
  данных», никогда не 0**: ноль расходов и отсутствие данных о расходах —
  разные утверждения, и второе выглядело бы как «привлекли бесплатно».

## Что появилось: `genderRatio` в `/admin/stats`

```jsonc
"genderRatio": {
  "male": 6, "female": 1, "unknown": 16, "total": 23,
  "malePctOfKnown": 85.7, "femalePctOfKnown": 14.3,
  "unknownPctOfTotal": 69.6
}
```

**Долю `unknown` обязательно называй вместе с раскладом.** Пол спрашивается на
одном из первых экранов онбординга, поэтому все, кто бросил регистрацию раньше,
остаются `null` — сегодня это 69.6% базы. «85.7% мужчин» без этой оговорки
описывает 30% базы как всю базу. Правильная формулировка: «среди назвавших пол
— 6 мужчин к 1 женщине; пол не указали 16 из 23».

Для матчинга перекос важен сам по себе: пул строго двусторонний, и число пар за
дроп упирается в меньшую сторону.

## Что появилось: поля матча в `/admin/matches`

У каждой строки, дополнительно к прежним:

| Поле | Тип | Смысл |
|---|---|---|
| `confirmed` | bool | оба сказали «да» |
| `ticketPurchased` | bool | оба слота оплачены |
| `ticketPurchasedAt` | ISO\|null | когда закрылся второй слот |
| `refunded` / `refundedSlots` | bool / int | вернулись ли деньги |
| `refundReason` | enum\|null | `no_show` / `ghost_during_scheduling` / `cancelled_before_date` / `unknown` |
| `noShow` | bool\|**null** | кого-то оставили ждать |
| `attendance` | enum | `met` / `not_met` / `disputed` / `unknown` |
| `ghostDuringScheduling` | bool | пропал на этапе планирования |
| `dateCompletedAt` | ISO\|null | когда свидание закрылось |

Четыре вещи, без которых эти поля читаются неверно:

1. **`noShow: null` — это «не знаем», а не «no-show не было».** Молчание после
   свидания — самый обычный исход. `false` означает «свидание точно
   состоялось».
2. **`attendance` и `dateCompletedAt` отвечают на РАЗНЫЕ вопросы.**
   `dateCompletedAt` — когда матч закрылся по таймеру (T+24h), независимо от
   того, пришёл ли кто-нибудь. Состоялась ли встреча — это `attendance`.
   Не используй `status === "completed"` как «свидание состоялось».
3. **`disputed` — реальное состояние, а не ошибка данных.** Стороны ответили
   по-разному: получасовая неловкая прогулка для одного «мы встретились», для
   другого «свидания не было». Показывай как есть, не схлопывай.
4. **`refundReason` выводится из терминального состояния матча**, потому что
   причина нигде не хранится: возврат срабатывает на шести путях (заморозка,
   удаление, модерация, экстренная отмена, оба финала stall-цепочки). Словарь
   описывает реальные пути; значений `NO_SHOW` / `GHOST_DURING_SCHEDULING`
   из исходного задания в API нет.

**Ни одно из этих полей не хранится в базе — все выводятся** из колонок,
которые продукт уже пишет. Практическое следствие: они заполнены на всей
истории матчей, а не с даты деплоя.

## Откуда берётся явка

С 2026-08-15 на T+24h сначала приходит вопрос «вы встретились?» с двумя
кнопками, и только на ответ «да» — форма обратной связи. На «нет» —
короткий разговор с четырьмя исходами. До этого продукт не знал о явке
ничего: `status='completed'` ставится по таймеру.

Два ограничения, которые надо держать в голове, читая цифры:

- **Только Telegram.** У пользователей приложения явка не спрашивается (нативный
  экран — отдельная задача), так что по ним `attendance` останется `unknown`.
  Это не отказ отвечать.
- **Ответ пишет только человек.** Улики (что писал агенту, прокси-чат) выбирают
  формулировку вопроса и никогда не пишут факт. Так что `attendance` — всегда
  чьё-то утверждение, а не вывод модели.

## Если поле пустое

| Что видишь | Что это значит | Что писать |
|---|---|---|
| `netPct: null` | нет подтверждённых матчей реальных пар | «нет данных» |
| `netPct: 0` | матчи есть, продаж нет | «0 продаж на N матчей» |
| `noShow: null` | никто не ответил | «нет данных», не «явка была» |
| `cacPerPaying: null` | расходов на трафик в продукте нет | «нет данных о расходах» |
| `attendance: "unknown"` | не ответили / мобильная рельса | не считать за «не встретились» |
| `truncated: true` в `userHealth` | база больше потолка скана | оговорить, что цифры частичные |

Общее правило: **пустое поле — это утверждение «мы не знаем», и его надо
передать словами.** Подставлять вместо него ноль — единственная ошибка в этом
разделе, которая делает отчёт хуже, чем его отсутствие.
