# Переход на ежедневный matching — план имплементации

> Основание: [DAILY_MATCHING_MIGRATION_AUDIT.md](DAILY_MATCHING_MIGRATION_AUDIT.md).
> Решения D1–D4 приняты владельцем продукта 2026-07-30, остальные —
> рекомендации ниже. Продуктовые инварианты (слепое решение, нет чата,
> lifetime-ban пары, одна живая пара, обязательная верификация, контактные
> рельсы, matching внутри города) не затрагиваются.

> требует `db:push`. Это делает и деплой, и откат существенно безопаснее.

## 1. Что выяснилось при проверке решений

### 1.1. TTL предложения задан ДВАЖДЫ, в двух разных файлах

Это не было видно в первом аудите и меняет объём Фазы 3.

| Константа | Файл | Кто читает |
|---|---|---|
| `MATCH_TTL_MS = 24h` | [`services/match-expiry.ts:36`](apps/bot/src/services/match-expiry.ts#L36) | **только** сам sweep, который реально гасит матч |
| `PROPOSAL_TTL_MS = 24h` | [`utils/countdown-plate.ts:26`](apps/bot/src/utils/countdown-plate.ts#L26) | кнопка обратного отсчёта ([`proposal-countdown.ts:125`](apps/bot/src/workers/proposal-countdown.ts#L125)), дедлайн-нудж ([`match-nudge.ts:127,167`](apps/bot/src/workers/match-nudge.ts#L127)), текст питча ([`pitch.ts:497`](apps/bot/src/handlers/matching/pitch.ts#L497)), поле `expiresAt` для iOS ([`matches-service.ts:319`](apps/bot/src/public/matches-service.ts#L319)) |

Сегодня они совпадают случайно. **Правка одной из них разъезжает то, что
пользователь видит, с тем, когда матч реально умирает** — причём разъезжается
это молча, и на всех поверхностях сразу, включая iOS. Первое действие Фазы 3 —
свести обе к одной функции.

### 1.2. Почему дедлайн лучше привязать к дропу, а не к моменту отправки

Ваш интент — «человек отвечает до следующего вечера, ~до 17:30, с запасом
на то, чтобы попасть в следующий дроп» — правильный. Но `dispatchedAt + 23:30`
его не даёт, потому что **`dispatchedAt` проставляется поштучно**: очередь
рассылки идёт с шагом 2 с ([`dispatch-queue.ts:18`](apps/bot/src/services/dispatch-queue.ts#L18)),
то есть 900-й по счёту матч отправляется через 30 минут после начала батча —
и его дедлайн приходится ровно на 18:00 следующего дня, то есть на сам батч.
Запас съеден, гонка вернулась. Плюс у разных людей дедлайны разъезжаются,
хотя дроп у них был общий.

**Предлагаемая форма:**

```
deadline = max(
  nextDrop(dispatchedAt) − DECISION_BUFFER,   // 17:30, одинаково для всех
  dispatchedAt + MIN_DECISION_MS              // страховка для внецикловых питчей
)
```

Что это даёт:
- дедлайн **17:30 ровно** у всех, независимо от позиции в очереди — ровно то,
  что вы описали;
- гонка с батчем исчезает **структурно**, а не за счёт удачно подобранного
  числа;
- кнопка обратного отсчёта и `expiresAt` в iOS показывают одно и то же число
  всем участникам дропа;
- `DECISION_BUFFER` из «того, что должно перекрыть рассылку» превращается в
  запас прочности.

Дополнительно: sweep expiry становится **preflight внутри батча** (прецедент
уже есть — preflight эмбеддингов, [`match-engine.ts:1751`](apps/bot/src/services/match-engine.ts#L1751)),
поэтому исход перестаёт зависеть от того, чей крон выстрелил первым.

`MIN_DECISION_MS` нужен только для питчей вне цикла (Rematch). При D8 = off
эта ветка мертва, но пусть будет — иначе включение Rematch обратно тихо
выдаст кому-то окно в полтора часа.

### 1.3. Cooldown 24 ч полностью аннулирует D1 — это не отдельная задача, а часть той же

`createProposedMatch` ставит `lastMatchedAt = now` в момент создания пары
([`match-engine.ts:1164`](apps/bot/src/services/match-engine.ts#L1164)), то есть
~18:00. Фильтр 7 требует `lastMatchedAt < now − 24ч`. На батче следующего дня
в 18:00 отсечка = вчерашние 18:00, строгое `<` не выполняется.

Итог: **человек, чей питч истёк в 17:30 специально ради попадания в дроп
18:00, всё равно из него выпадет** — и без единой строчки в логах.
Ради этого и вводится D7. Пороговое значение 6 ч выбрано так, чтобы фильтр
никогда не срабатывал при суточной каденции (её роль дросселя выполняет сам
батч), но оставался защитой от мгновенного повторного матча на внецикловом
пути.

### 1.4. Почему Rematch стоит выключить, а не настраивать

При суточных дропах: блэкаут 6 ч = 25% суток, кулдаун 24 ч = ровно интервал
дропа, а обещание «я продолжил искать между дропами» продаёт то, что завтра
и так придёт бесплатно. Плюс внецикловый питч конфликтует с общим дедлайном
из §1.2. Настройка всех четырёх параметров — работа, которая при этом не
восстанавливает ценность функции. Выключение — одна env-переменная и ноль
кода; включить обратно можно в любой момент, если пилот покажет обратное.

## 2. Архитектурный каркас: профиль каденции

Корневая причина того, что смена частоты задевает 15 подсистем — **длительность
цикла нигде не выражена как величина**. Она размазана по хардкодам: 8 дней в
`getPreviousBatchDate`, 48 ч rush-окна, 6 ч блэкаута, 24 ч TTL и кулдауна.

Вводится единый профиль — он же механизм отката (§6):

```ts
// packages/shared/src/cadence.ts   (новый файл)
export interface DropCadence {
  cron: string;                  // "0 18 * * *"
  intervalMs: number;            // 24 ч
  decisionBufferMs: number;      // 30 мин — дедлайн = дроп − это
  minDecisionMs: number;         // пол для внецикловых питчей
  cooldownMs: number;            // D7
  starvationAlpha: number;       // D6
  famineNoticeIntervalMs: number;// D4
  famineDiscountMinDays: number; // D5
  profilerRushWindowMs: number;  // D9
  stallCheckInMs: number;
  stallTimeoutMs: number;
  proposalNudgeOffsets: number[];
}

export const CADENCES: Record<"weekly" | "daily", DropCadence> = { … };
export const CADENCE = CADENCES[process.env.DROP_CADENCE ?? "weekly"];
```

Правила:
- **Ни один потребитель не читает `process.env` напрямую** — только `CADENCE`.
- Профиль `weekly` воспроизводит сегодняшнее поведение **бит в бит**. Это
  проверяемое условие: после Фазы 1–5 весь существующий набор тестов должен
  проходить при `DROP_CADENCE=weekly` без правок ожиданий.
- `MATCH_CRON_SCHEDULE` остаётся как аварийный override расписания, но
  перестаёт быть способом сменить каденцию.

## 3. Фазы имплементации

Порядок продиктован зависимостями. Каждая фаза оставляет систему рабочей и
деплоится отдельно; фазы 1–5 деплоятся с `DROP_CADENCE=weekly`, то есть
**без изменения поведения в проде**. Реальное переключение — только на шаге §5.

- Тест: `weekly` профиль равен сегодняшним константам (защита от дрейфа).

### Фаза 3 — Жизненный цикл предложения
- **Новый `services/proposal-deadline.ts`** — единственный источник дедлайна
  (§1.1, §1.2): `deadlineFor(dispatchedAt): Date`.
- Перевести на него **все семь** мест: `match-expiry.ts:36,93`,
  `countdown-plate.ts:26`, `proposal-countdown.ts:125`, `match-nudge.ts:127,167`,
  `pitch.ts:497`, `matches-service.ts:319`. Обе старые константы удалить.
- `expireStaleMatches` — с `dispatchedAt < cutoff` на `deadline < now`
  (запрос перестаёт быть однородным по `dispatchedAt`; проверить, что индекс
  `(status, createdAt)` всё ещё пригоден, иначе фильтровать по `status` +
  считать дедлайн в памяти — объёмы это позволяют).
- **Expiry как preflight внутри батча** — по образцу preflight эмбеддингов.
- Каденция ноджей ([`match-nudge.ts:43-53`](apps/bot/src/workers/match-nudge.ts#L43))
  из профиля. Для суточного: `2ч / 8ч / дедлайн −1.5ч`. Проверить, что второй
  нодж не проваливается целиком в quiet hours 23:00–09:00 (при дропе 18:00
  он попадает на 02:00 → отложится до 09:00; это приемлемо и даже удачно —
  утреннее напоминание за 8.5 ч до дедлайна, но должно быть осознанным, а не

- Stall-цепочка ([`match-stall.ts:37-48`](apps/bot/src/services/match-stall.ts#L37)):
  для суточного профиля `checkIn 12ч`, `timeout 24ч`, venue-ноджи `3ч/6ч` —
  иначе один «призрак» стоит партнёру два дропа.

**Критерий выхода:** дедлайн, показанный в кнопке, в тексте питча, в дедлайн-
ндже и в `expiresAt` для iOS — одно и то же число. Тест на это обязателен.

## 4. Порядок деплоя

Схема БД не меняется → `db:push` не нужен, но `pnpm db:drift-check` остаётся
обязательным гейтом по регламенту.

1. Фазы 0–5 катятся в прод **с `DROP_CADENCE=weekly`**. Поведение не меняется,
   код проверяется в бою.
2. Фаза 6 (копирайт) — тоже в weekly-режиме: формулировки должны быть
   корректны в обеих каденциях, иначе переключение потребует второго деплоя.
3. Прогон на `@gennetytestbot` в `daily` — полный цикл: дроп → питч → дедлайн
   17:30 → expiry → следующий дроп, с реальным попаданием освобождённых
   пользователей в него.
4. Прод: `REMATCH_FEATURE_ENABLED=false`, затем `DROP_CADENCE=daily`,
   `pm2 restart gennety-bot --update-env`.

**Проверка того, что переключение реально произошло** — по строке крона в
логе старта, как это уже делалось для Rematch и pre-match announce:
`[cron] … "0 18 * * *"` вместо `"0 18 * * 4"`.

| Что | Где | Признак проблемы |
|---|---|---|
| Освобождённые попадают в следующий дроп | `[weekly-batch] eligible=… pairs=…` | `eligible` не растёт после expiry-волны → D7 не сработал |
| Дедлайн един для всех | кнопка отсчёта vs `expiresAt` | расхождение → §1.1 не доведена |
| Объём famine-DM | `no_match_notices` по дням | больше одного на пользователя за 2 дня |
| Profiler не в вечном rush | размер батча | всегда 2 вопроса |
| Расход пула | уникальные пары в `matches` | скорость исчерпания vs приток регистраций (§7) |

## 5. Риски, специфичные для выбранной конфигурации

- **Дедлайн 17:30 и дроп 18:00 — 30 минут на всё.** Запас перекрывает рассылку
  и гранулярность sweep'а, но при росте пула его нужно пересматривать. Именно
  поэтому expiry делается preflight'ом батча: тогда 30 минут — запас прочности,
  а не механизм.
- **Quiet hours съедают 10 из 24 часов цикла.** При дропе в 18:00 «громкого»
  времени до полуночи ~5 часов. Второй нодж уезжает на утро. Это приемлемо,
  но означает, что реальное окно внимания пользователя короче номинального.
- **Занятые пользователи пропускают дропы** — принято в D2, но копирайт должен
  это отражать, иначе честное решение выглядит как поломка.
- **Расход пула ×7 необратим** — см. §7.

## 6. Откат

`DROP_CADENCE=weekly` + `pm2 restart --update-env`. Кода не трогаем, схемы нет.

**Что откат не вернёт автоматически:**

1. **`standbyCount` / `missedWeeks` инфлированы** — значение «14» означало 14
   дней, в weekly-профиле прочитается как 14 недель → мгновенный максимальный
   starvation у всех. **Требуется скрипт нормализации** (деление на 7 либо
   обнуление). Это единственный шаг отката, который не делается одной
   переменной, и его нужно написать **до** переключения, а не после.
2. **Скидки famine**, уже выданные, остаются валидными — выданная льгота не
   отзывается. Допустимая потеря.
3. **`NoMatchNotice`** — плотная суточная история; после Фазы 4 `computeTier`
   считает дни, а не строки, поэтому тиры не завышаются. Один из немногих
   случаев, где правка ради daily заодно чинит откат.
4. **Lifetime-ban пары необратим.** Неделя суточного режима сжигает столько
   уникальных пар, сколько семь недель недельного. Откат вернёт каденцию, но
   не пул.

## 7. Открытый вопрос, блокирующий запуск (не имплементацию)

**D10 — политика исчерпания пула.** Lifetime-ban + matching внутри города
(Киев — единственный запущенный рынок) означают, что личное множество
кандидатов конечно и строго убывает: при N пользователях противоположного
пола человек получает максимум N дропов за всю жизнь аккаунта. Суточный ритм
сжимает N недель в N дней.

Продовый базлайн на последний деплой: 9 пользователей, в Киеве 6 —
**4 мужчины, 0 женщин**, 0 матчей за всю историю. При таком пуле ежедневный
батч производит только ежедневный famine-DM.

Нужен явный ответ на два вопроса:
1. Что продукт говорит человеку, для которого пул кончился? Сегодня — ничего:
   он попадает в бесконечный famine, где копирайт ежедневно повторяет «это
   про пул, не про тебя», что формально верно и звучит как издевательство.
2. При каком размере и притоке пула пилот вообще запускается? Ежедневная
   каденция осмысленна, только если пул растёт быстрее, чем потребляется —
   это условие запуска, а не деталь реализации.

Имплементацию (Фазы 0–8) это не блокирует: весь код катится в weekly-режиме
и ничего не меняет до переключения. Блокирует именно шаг 4 деплоя.

**Рекомендация:** пилот на ограниченной когорте с заранее назначенным
критерием остановки, а не переключение всей базы — обратимость каденции
высокая, обратимость пула нулевая.
