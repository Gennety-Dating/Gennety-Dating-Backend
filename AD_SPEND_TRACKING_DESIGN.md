# Ввод расходов на трафик — дизайн (предложение, не реализация)

> Статус: **предложение к обсуждению.** Ничего из описанного здесь не
> реализовано. Решение — за фаундером; реализация отдельным спринтом.
>
> Зачем документ существует: CAC, LTV:CAC и ROAS сейчас посчитать нечем — в
> продукте нет ни одного источника данных о деньгах, потраченных на
> привлечение. Метрики выручки уже есть (`GET /admin/analytics/monetization`,
> `GET /admin/purchases`); не хватает ровно второй половины дроби.

## Что уже есть, и почему это определяет дизайн

Три вещи в коде задают форму решения ещё до выбора варианта:

1. **Словарь каналов уже существует** — `normalizeChannel`
   (`admin/utils/growth.ts`) приводит `User.referralSource` к
   `organic` | `referral` | `mobile` | `web:*` | `tg:<campaign>`.
   **Расходы обязаны храниться в ЭТОМ словаре**, иначе можно будет посчитать
   только общий CAC и никогда — CAC по каналам, ради которого всё и затевается.
   Это единственное по-настоящему жёсткое требование к схеме.
2. **Недельные корзины уже существуют** — `weekStartOf`
   (`admin/utils/monetization.ts`) даёт ISO-понедельник в UTC. Расходы кладутся
   в те же корзины, что и когорты выручки, иначе периоды не сойдутся.
3. **Тестовые аккаунты уже исключаются** — `admin/utils/user-health.ts`
   (`syntheticAt` + `ADMIN_TEST_TELEGRAM_IDS`). Знаменатель CAC берёт вердикт
   оттуда, а не выводит правило заново.

## Схема хранения (одинакова для всех четырёх вариантов)

```prisma
model AdSpend {
  id            String   @id @default(uuid())
  /// Словарь normalizeChannel: organic | referral | mobile | web:* | tg:<campaign>
  channel       String
  /// ISO-понедельник UTC (weekStartOf). Недельная гранулярность — см. ниже.
  periodStart   DateTime
  /// Сумма в валюте, в которой реально платили.
  amount        Int      // минорные единицы (копейки/центы)
  currency      String   // ISO-4217: UAH, USD, EUR
  /// Пересчёт в USD-центы ПО КУРСУ НА МОМЕНТ ВВОДА, заморожен навсегда.
  amountUsdCents Int
  note          String?
  createdAt     DateTime @default(now())
  updatedAt     DateTime @updatedAt

  @@unique([channel, periodStart])
  @@index([periodStart])
}
```

Три решения внутри схемы, каждое лечит конкретную будущую боль:

- **`@@unique([channel, periodStart])`** — повторный ввод той же недели
  обновляет строку, а не удваивает расход. Без этого первый же случай «ой, я
  ввёл дважды» тихо режет CAC вдвое.
- **`amountUsdCents` заморожен при вводе.** Пересчитывать историю по текущему
  курсу нельзя: CAC за июль будет меняться каждый день, и сравнение недель
  перестанет что-либо значить. Это то же правило, по которому
  `ticket_ledger.amountStars` и `venue_change_purchases.amountStars` фиксируют
  цену в момент события (ARCHITECTURE → Purchase ownership).
- **Неделя, а не день.** Дневной CAC при текущих объёмах — шум: одна
  регистрация двигает его на десятки процентов. Недельная корзина совпадает с
  `weekStartOf`, с когортами монетизации и с ритмом отчёта Hermes.

## Варианты ввода

### 1. Опросник в боте (еженедельный диалог с фаундером)

Фаундер-бот раз в неделю спрашивает: «сколько потратил по каналам за прошлую
неделю?», собирает ответы, пишет в `ad_spend`.

- **Плюсы.** Push, а не pull: не надо помнить. Фаундер уже живёт в этом чате —
  туда приходят регистрации, свидания и покупки. Ноль нового UI.
- **Минусы, и главный из них неочевиден.** Фаундер-бот сегодня **односторонний**:
  `services/founder-notify.ts` только отправляет, у него нет ни одного
  обработчика апдейтов и нет сессии. Ввод диалогом — это новый бот-раннер (или
  ветка в основном боте) плюс машина состояний плюс валидация свободного текста
  на числах и валютах. Это самая дорогая из «дешёвых» опций.
- **Трудоёмкость.** Бэкенд: средняя (обработчик апдейтов + FSM + парсинг).
  UI: нет.

### 2. Загрузка CSV в дашборд

Фаундер выгружает таблицу из рекламного кабинета и заливает файлом.

- **Плюсы.** Совпадает с тем, как рекламные площадки реально отдают данные.
  Закрывает бэкфилл: десять недель за один заход.
- **Минусы.** Нужен парсер, обработка ошибок построчно и **UI сопоставления
  колонок**: в выгрузке Meta канал называется не так, как в нашем
  `normalizeChannel`, и кто-то должен их связать. Для одного человека, вводящего
  одно число в неделю, формат файла — избыточная механика. Плюс каналы, которые
  здесь реально важны (закупка в Telegram-каналах, посты у блогеров), никаких
  выгрузок не имеют вообще — их всё равно придётся вводить руками.
- **Трудоёмкость.** Бэкенд: средняя. UI: высокая (загрузка + маппинг + превью).

### 3. Ручная форма в дашборде — **рекомендуется**

Четыре поля (канал, неделя, сумма, валюта), под ними таблица введённого с
правкой и удалением.

- **Плюсы.** Самый дешёвый настоящий UI: без парсинга, без новых возможностей
  бота, без секретов. Стоит там, где фаундер и так читает цифры, — расход и CAC
  на одном экране. Канал выбирается из списка **реально встречавшихся**
  `normalizeChannel`-значений, поэтому опечатка не создаёт «канал-призрак», на
  который ничего не сматчится.
- **Минусы.** Pull, а не push: никто не напомнит. Пропущенная неделя тихо даёт
  завышенный CAC.
  **Смягчение — и это то же правило, что уже задано для карточек метрик:**
  неделя без строки показывается как «нет данных», а не как 0. Ноль расходов и
  отсутствие данных — разные утверждения, и второе никогда не должно выглядеть
  как «привлекли бесплатно».
- **Трудоёмкость.** Бэкенд: низкая (`GET /admin/ad-spend`,
  `POST /admin/ad-spend` с upsert по уникальному ключу, `DELETE`).
  UI: низкая (одна страница, одна форма, одна таблица).

### 4. Интеграция с рекламным кабинетом (Meta / Google Ads API)

- **Плюсы.** Без человека, точно, посуточно, с разбивкой до кампании.
- **Минусы.** OAuth, refresh токенов, отдельная схема на каждую площадку, воркер
  синхронизации, ещё одни секреты на дроплете. И главное: на текущих объёмах это
  автоматизация примерно двух минут в неделю. Плюс площадки без API (Telegram,
  блогеры) всё равно остаются на ручном вводе — то есть форма из варианта 3
  нужна в любом случае, даже после интеграции.
- **Трудоёмкость.** Бэкенд: высокая. UI: средняя (подключение аккаунта, статус
  синка).

## Рекомендация

**Вариант 3 (ручная форма) как основа + напоминание из варианта 1 в самой
дешёвой форме.**

Напоминание — не диалог, а обычное еженедельное сообщение в фаундерский ops-DM
со ссылкой на форму. Это одно уведомление через уже существующий
`founder-notify.ts` и **никакой машины состояний**: закрывает единственный
реальный минус варианта 3 (никто не напомнит), не платя за единственный реальный
минус варианта 1 (у бота нет обработчика апдейтов).

Вариант 4 — не раньше, чем ручной ввод начнёт занимать заметное время, то есть
после нескольких одновременных платных каналов с API.

## Что станет считаться, когда расходы появятся

Все формулы — на неделю, знаменатели без тестовых/синтетических аккаунтов.

| Метрика | Формула | Оговорка |
|---|---|---|
| CAC на платящего | `spendUsd(week) / новых платящих(week)` | «Новый платящий» = тот, у кого **первая** оплата попала в неделю. Считать «всех, кто платил» нельзя — повторные покупатели раздуют знаменатель и занизят CAC. Источник: `loadPayerIndex` (`services/purchases.ts`), поле первой оплаты уже есть. |
| CAC на активного | `spendUsd(week) / новых active+verified(week)` | Знаменатель — тот же, что у `funnel.active_verified`. |
| LTV : CAC | `LTV когорты / CAC когорты` | LTV — пожизненные `usdCents` из `loadPayerIndex`. Осторожно: у молодой когорты LTV занижен по построению; в `monetization.ts` уже есть `COHORT_MATURITY_DAYS` (14) и флаг `censored` — использовать их, а не считать незрелые когорты наравне. |
| ROAS | `revenueUsd(week) / spendUsd(week)` | Выручка берётся из окна, а не «пожизненный спенд тех, кто платил на этой неделе» — грабли уже описаны в шапке `monetization.ts`, п.5. |
| CPL по каналам | `spendUsd(channel, week) / регистраций(channel, week)` | L = регистрация, не клик. |
| CPC | **не считается** | Кликов у нас нет: трекинга переходов не существует, `referralSource` фиксируется уже на регистрации. Показывать CPC, подставив вместо кликов регистрации, — назвать одну метрику именем другой. Либо приезжает трекинг переходов, либо метрики нет. |
| Затраты vs выручка по каналам | `spendUsd(channel)` рядом с `revenueUsd(channel)` | Разрез по каналам в выручке уже есть — `segments.byChannel` в `/admin/analytics/monetization`. |

**Правило отображения до появления данных:** карточка показывает «нет данных»,
а не 0, — и это касается не только периода до внедрения, но и любой отдельной
недели, за которую расход не введён.

## Чего этот дизайн НЕ решает

- **Атрибуцию.** `referralSource` — first-touch и ставится один раз при создании
  аккаунта (PRODUCT_SPEC §3.9/§3.10). Пользователь, увидевший рекламу и
  пришедший через неделю по прямой ссылке, засчитается в `organic`. CAC по
  каналам поэтому — оценка сверху для платных каналов и снизу для `organic`.
  Ввод расходов этого не чинит; чинит только трекинг переходов.
- **Возвраты в ROAS.** Выручка уже считается без возвращённых покупок
  (`refund_failed` при этом считается — деньги всё ещё у нас), так что ROAS
  наследует это правило автоматически. Отдельного решения не требует, но знать
  об этом надо при сверке с выпиской платёжной системы.
