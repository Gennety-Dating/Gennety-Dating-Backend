# Ввод расходов на трафик — реализовано

> Статус: **реализовано.** Схема, админ-роуты, форма и таблица на дашборде,
> еженедельное напоминание фаундеру и вычисление CAC/LTV:CAC/ROAS — всё уже
> в проде. Этот файл больше не предложение; он держит рассуждение за формой,
> которую выбрали, потому что само по себе оно не читается из кода. Ниже:
> четыре рассмотренных варианта ввода (§«Варианты ввода», выбран №3) — как
> решённая история, не как открытый вопрос; и два-осевая модель канал×
> категория, к которой пришли уже после первой версии этого документа.

Раньше документ был предложением: CAC, LTV:CAC и ROAS считать было нечем — в
продукте не было ни одного источника данных о деньгах, потраченных на
привлечение, хотя выручка уже считалась (`GET /admin/analytics/monetization`,
`GET /admin/purchases`). Не хватало ровно второй половины дроби. Теперь она
есть — `apps/bot/src/admin/utils/ad-spend.ts` (чистая функция,
`computeAcquisitionCost`), `apps/bot/src/admin/routes/ad-spend.ts` (CRUD),
`GET /admin/dashboard`'s `adSpendByChannel`/`totalMarketingSpendUsdCents` и
четыре ранее захардкоженных `null` в `derived`, плюс страница `/ad-spend` на
дашборде (`~/Desktop/gennety-admin-dashboard`).

## Что уже было, и почему это задало форму решения ещё до выбора варианта

Три вещи в коде задавали форму решения ещё до выбора варианта ввода — это
рассуждение не изменилось с первой версии документа:

1. **Словарь каналов уже существовал** — `normalizeChannel`
   (`admin/utils/growth.ts`) приводит `User.referralSource` к
   `organic` | `referral` | `mobile` | `web:*` | `tg:<campaign>`.
   **Расходы обязаны храниться в ЭТОМ словаре**, иначе можно было бы
   посчитать только общий CAC и никогда — CAC по каналам, ради которого всё и
   затевается. Цифровая реклама и QR-код на офлайн-мероприятии в этом смысле
   не различаются: обе приводят к телеграм-диплинку с `start`-параметром, то
   есть офлайн-событие — не особый случай на оси канала, а канал с более
   длинным окном атрибуции на оси категории (см. ниже). `mobile:utm=…`,
   упомянутый в комментарии `growth.ts` как формат канала, никогда не был
   реализован — проверено грепом по всему боту, ни одного совпадения кроме
   этого комментария; атрибуция платных iOS-каналов сегодня не существует и
   вне охвата (платных iOS-кампаний нет).
2. **Тестовые аккаунты уже исключались** — `admin/utils/user-health.ts`
   (`syntheticAt` + `ADMIN_TEST_TELEGRAM_IDS`). Знаменатель CAC берёт вердикт
   оттуда, а не выводит правило заново — реализовано ровно так:
   `computeAcquisitionCost` принимает уже отфильтрованный `users: readonly
   AcquisitionCostUserInput[]`, а не читает Prisma сам; фильтрация происходит
   на уровне роута, тем же вызовом, что уже кормит `funnel`/`userHealth`.

## Две оси: канал и категория (решено после первой версии документа)

Первая версия схемы держала одну ISO-недельную корзину на все расходы. Она
не пережила первый разговор о реальных типах трат: перформанс-реклама
конвертит за часы, сарафанное радио с офлайн-события тянется неделями. Одна
календарная неделя не может выразить оба темпа, поэтому расход теперь несёт
**свободный диапазон дат** (`periodStart`/`periodEnd`) и **категорию**, а
категория — а не канал — решает, сколько дней ПОСЛЕ окончания периода ещё
засчитывать конверсии, прежде чем считать запись «созревшей».

```ts
// apps/bot/src/admin/utils/ad-spend.ts
export const AD_SPEND_CATEGORIES = [
  "performance_ads", "influencer", "offline_event",
  "content_production", "agency", "other",
] as const;

export const AD_SPEND_ATTRIBUTION_WINDOW_DAYS: Record<AdSpendCategory, number | null> = {
  performance_ads: 3,
  influencer: 14,
  offline_event: 28,
  content_production: null,   // не покупает атрибутируемое привлечение вовсе
  agency: null,                // — retainer, продакшн, ничего трекать не с чем
  other: 7,
};
```

`null` — это не «окно ещё не решили», это «эта категория не покупает
привлечение, которое можно отследить». `content_production` (съёмка ролика)
и `agency` (ретейнер) считаются в общей сумме трат фаундера, но исключены из
любого CAC/CPL/ROAS-расчёта — с ними физически не с чем сопоставлять
регистрацию. Такая запись обязана быть залогирована на канал-часовню
`"unattributed"` (`UNATTRIBUTED_CHANNEL`), проверяется как сервером
(`categoryRequiresUnattributed()`, роут отказывает при несовпадении), так и
формой на дашборде — двойная проверка, потому что дашборд — не единственный
клиент этого API.

Числа — настраиваемые дефолты, а не постоянная величина, тот же статус, что
`COHORT_MATURITY_DAYS` носит в `monetization.ts`: реальной кривой лага
конверсии пока строить не из чего, платящих на момент написания — ноль.

## Схема хранения

```prisma
model AdSpend {
  id             String   @id @default(uuid()) @db.Uuid
  /// normalizeChannel-совместимый ключ (tg:<slug>, mobile, referral, organic)
  /// или буквально "unattributed" для трат без канала атрибуции вовсе.
  channel        String
  /// Одно из AD_SPEND_CATEGORIES. Обычная строка, не Prisma-enum — та же
  /// причина, что у Match.source: новая категория не стоит миграции.
  category       String
  periodStart    DateTime @map("period_start")
  periodEnd      DateTime @map("period_end")
  amount         Int
  /// ISO-4217.
  currency       String
  /// USD-центы, заморожены при вводе — никогда не пересчитываются задним
  /// числом при движении курса, то же правило, что ticket_ledger.amountStars.
  amountUsdCents Int      @map("amount_usd_cents")
  note           String?
  createdAt      DateTime @default(now()) @map("created_at")
  updatedAt      DateTime @updatedAt @map("updated_at")

  @@unique([channel, category, periodStart, periodEnd])
  @@index([periodStart])
  @@map("ad_spend")
}
```

Повторный ввод той же комбинации канал+категория+диапазон обновляет строку, а
не удваивает расход — тот же защитный смысл, что был у `@@unique([channel,
periodStart])` в первой версии, расширенный под свободные диапазоны.
`amountUsdCents` фиксируется при вводе по той же причине, что и раньше:
пересчитывать историю по текущему курсу нельзя, иначе CAC за прошлый месяц
менялся бы каждый день, и сравнение периодов переставало бы что-либо значить.

## Варианты ввода (решённая история)

Рассмотрены и сравнены до выбора; ниже — как это выглядело на момент решения.
Выбран **вариант 3**.

### 1. Опросник в боте (еженедельный диалог с фаундером)

Фаундер-бот раз в неделю спрашивает: «сколько потратил по каналам за прошлую
неделю?», собирает ответы, пишет в `ad_spend`.

- **Плюсы.** Push, а не pull: не надо помнить. Фаундер уже живёт в этом чате.
- **Минусы, и главный из них неочевиден.** Фаундер-бот — **односторонний**:
  `services/founder-notify.ts` только отправляет, у него нет ни одного
  обработчика апдейтов и нет сессии. Ввод диалогом — это новый бот-раннер (или
  ветка в основном боте) плюс машина состояний плюс валидация свободного текста
  на числах и валютах. Самая дорогая из «дешёвых» опций.
- **Трудоёмкость.** Бэкенд: средняя. UI: нет.

### 2. Загрузка CSV в дашборд

Фаундер выгружает таблицу из рекламного кабинета и заливает файлом.

- **Плюсы.** Совпадает с тем, как площадки реально отдают данные. Закрывает
  бэкфилл разом.
- **Минусы.** Нужен парсер и **UI сопоставления колонок**: канал в выгрузке
  Meta называется иначе, чем в `normalizeChannel`. А каналы, которые здесь
  реально важны (закупка в Telegram-каналах, посты у блогеров), никаких
  выгрузок вообще не имеют — их всё равно вводить руками.
- **Трудоёмкость.** Бэкенд: средняя. UI: высокая.

### 3. Ручная форма в дашборде — **выбрано и реализовано**

Форма (канал, категория, диапазон дат, сумма+валюта, авто-подставленный
USD-эквивалент, заметка) плюс таблица введённого с правкой и удалением.
`/ad-spend` на дашборде.

- **Плюсы.** Самый дешёвый настоящий UI. Стоит там, где фаундер и так читает
  цифры — расход и CAC на одном экране. Канал выбирается из списка **реально
  встречавшихся** `normalizeChannel`-значений (`GET /admin/ad-spend/channels`,
  объединяет уже засветившиеся `referralSource` реальных пользователей и уже
  залогированные каналы расходов), так что опечатка не создаёт
  «канал-призрак», на который ничего не сматчится — ни на стороне сервера,
  ни в форме.
- **Минусы.** Pull, а не push: никто не напомнит сам по себе. Смягчено
  еженедельным напоминанием (см. ниже) — не диалогом, одним сообщением.
  **И то же правило отображения, что уже задано для карточек метрик:**
  период без строки показывается на дашборде как «нет данных», а не как 0.
- **Трудоёмкость.** Реализовано как описано.

### 4. Интеграция с рекламным кабинетом (Meta / Google Ads API)

- **Плюсы.** Без человека, точно, посуточно.
- **Минусы.** OAuth, refresh токены, отдельная схема на каждую площадку,
  воркер синка, ещё секреты на дроплете — при текущих объёмах это
  автоматизация двух минут в неделю. Площадки без API (Telegram, блогеры) всё
  равно остаются на ручном вводе — форма варианта 3 нужна в любом случае.
- **Трудоёмкость.** Не сделано; не раньше, чем ручной ввод начнёт занимать
  заметное время.

Напоминание реализовано как одно еженедельное сообщение в фаундерский ops-DM
(`notifyFounderAdSpendReminder`, тот же `Api`-инстанс, что и
`notifyFounderWeeklyMatches`) со ссылкой на `/ad-spend` — **без машины
состояний**: закрывает единственный реальный минус варианта 3, не платя за
минус варианта 1 (у бота нет обработчика апдейтов).

## Что считается

`computeAcquisitionCost` (`apps/bot/src/admin/utils/ad-spend.ts`) — чистая
функция, без Prisma внутри; роут собирает входные массивы (расходы,
реальные пользователи с уже посчитанным `channel`, `loadPayerIndex()`) и
передаёт их. Формулы не завязаны на календарную неделю — они завязаны на
**окно записи**: `periodEnd + AD_SPEND_ATTRIBUTION_WINDOW_DAYS[category]`.

| Метрика | Что это | Оговорка |
|---|---|---|
| `totalMarketingSpendUsdCents` | Сумма ВСЕХ строк, любая категория | П&Л-цифра фаундера — шире, чем то, из чего считается CAC. Включает `content_production`/`agency`. |
| `attributableSpendUsdCents` | Сумма строк, чья категория имеет окно И чей канал матчится хоть одному пользователю | То, что реально кормит CAC. `unattributed` и записи с `window = null` сюда не попадают. |
| `cacPerPayingUsdCents` (по каналу и суммарно) | `spendUsdCents / |{payerIds}|` через `divCents()` | Платящий засчитывается каналу, если `firstPaidAt` не позже конца окна записи (`periodEnd + window`), а сам пользователь зарегистрировался внутри `[periodStart, periodEnd]` и его `channel === entry.channel`. |
| `cacPerActiveUsdCents` | То же, знаменатель — `active && verified` внутри диапазона | Тот же знаменатель, что `funnel.active_verified`. |
| `ltvCac` | `(pожизненные usdCents платящих / их число) / cacPerPayingUsdCents` | **Не** «выручка в окне» — это **сознательное** расхождение с правилом `monetization.ts` (revenue-in-window защищает НЕДЕЛЬНУЮ выручку от загрязнения повторными покупками одного и того же периода). Здесь когорта определена событием ПРИВЛЕЧЕНИЯ, а не окном покупки: раз пользователь атрибутирован этой трате, вся ценность, которую он принёс с тех пор, и есть ответ на вопрос «окупилась ли трата». |
| `roas` | `(та же когортная выручка) / attributableSpendUsdCents` | Та же выручочная база, что у `ltvCac`, намеренно — иначе два «похожих» числа расходились бы по немотивированной причине. |
| `matured` (по каналу и суммарно) | `true`, если для КАЖДОЙ атрибутируемой строки текущее время уже прошло конец её окна | Незрелая цифра — не «нет данных», а «данные ещё собираются»; на дашборде это бейдж «Still accruing» рядом с числом, а не блокировка. |
| CPL по каналам | `spendUsdCents / |{signupIds}|` через `divCents()` | Регистрации дедуплицируются по `Set`, так что две пересекающиеся по времени записи на один канал не удваивают регистрацию. |
| CPC | **не считается** | Кликов нет: трекинга переходов не существует, `referralSource` фиксируется уже на регистрации. |

**`divCents()` — правило отображения, а не деталь реализации:**

```ts
function divCents(numerator: number, denominator: number): number | null {
  if (denominator <= 0 || numerator <= 0) return null;
  return Math.round(numerator / denominator);
}
```

Ноль или отрицательный знаменатель/числитель — это `null`, никогда `0` и
никогда `Infinity`. «Нет данных» и «привлекли бесплатно» — разные
утверждения, и второе никогда не должно выглядеть как первое; на дашборде
это карточки `BlockedCard` в сером тексте с причиной вместо белой цифры.
Это правило распространяется на КАЖДЫЙ период без строки, а не только на
время до внедрения фичи.

## Чего эта модель НЕ решает

- **Атрибуцию.** `referralSource` — first-touch и ставится один раз при
  создании аккаунта (PRODUCT_SPEC §3.9/§3.10). Пользователь, увидевший
  рекламу и пришедший через неделю по прямой ссылке, засчитается в `organic`.
  CAC по каналам поэтому — оценка сверху для платных каналов и снизу для
  `organic`. Ввод расходов этого не чинит; чинит только трекинг переходов,
  которого нет.
- **Возвраты в ROAS.** Выручка (через `loadPayerIndex`) уже считается без
  возвращённых покупок (`refund_failed` при этом считается — деньги всё ещё у
  нас), так что `ltvCac`/`roas` наследуют это правило автоматически.
