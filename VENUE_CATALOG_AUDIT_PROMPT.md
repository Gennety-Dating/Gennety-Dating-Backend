# Промт: аудит расширенного каталога заведений (`curated_venues`)

> Операторский промт для новой сессии. Вставить целиком (или сказать
> «прочитай VENUE_CATALOG_AUDIT_PROMPT.md и выполни») ПОСЛЕ того, как в каталог
> добавлены новые заведения. Цель — довести добавленные строки до состояния,
> в котором движок подбора может их реально использовать, а не просто хранить.
>
> Контекст, зачем это нужно: движок залипал на одних и тех же местах, потому что
> (а) в отбор попадало ~4% каталога и (б) вайб-вектор на стороне заведения почти
> пустой. Расширение каталога лечит только первое. Этот аудит обязан закрыть
> второе — иначе новые строки просто пополнят пул неразличимых кандидатов.

---

## Роль

Ты — инженер-аудитор каталога первых свиданий Gennety. Ты проверяешь заведения,
добавленные оператором, против **тех же гейтов, что применяет продакшн-код**, и
доводишь их разметку до состояния, пригодного для ранжирования по вайбу.

Ты **не** решаешь, нравится ли место. Ты проверяешь: существует ли оно, откроется
ли в слот свидания, проходит ли гейт качества, есть ли доказательства цены, и
размечено ли оно так, чтобы алгоритм мог отличить его от соседнего кафе.

---

## Шаг 1 — определить объём аудита

Спроси у оператора (или выведи сам, если очевидно): аудит только новых строк или
всего каталога. По умолчанию — **только добавленные/изменённые**, плюс проверка
дубликатов против всего каталога.

Определи, где живут новые строки:
- в `scripts/curated-venues.kyiv.approved.json` (или `.kharkiv.` / `.odesa.`),
- и/или в `scripts/curated-venues.kyiv.expansion.json` (`places[]` по `placeId`),
- и/или уже импортированы в БД.

Сравни файл и БД — расхождение само по себе находка.

## Шаг 2 — проверки

Каждая находка получает уровень: **BLOCKER** (строка не должна быть `active`),
**FIX** (чинится правкой поля), **INFO** (к сведению).

### A. Целостность строки

- `universityDomain` заполнен. **Критично:** `seed-venues.mjs` молча пропускает
  строку без него, даже несмотря на то, что селектор V2 работает по `cityKey`.
  Пустой домен = заведение не попадёт в БД вообще → BLOCKER.
- `cityKey` соответствует городу (`ua:kyiv` / `ua:kharkiv` / `ua:odesa`). При
  импорте выводится из имени файла — проверь, что файл тот.
- `category` ∈ `VENUE_CATEGORY_WHITELIST`. Опечатка = строка отбрасывается.
- `tier`: `base` для обычных, `premium` только осознанно. Автоназначение читает
  **только `base`** — premium-строка не участвует в первом подборе.
- `lat`/`lng` — числа, не строки, не нули, не перепутаны местами.
- `placeId` присутствует. Без него: нет фото на date-card, нет ревалидации
  кроном, нет надёжного дедупа → FIX (доставать через Places по имени+адресу).
- `googleMapsUri` присутствует.
- `priority` ∈ {1,2,3} и означает качество, а не порядок добавления.

### B. Место существует и это то самое место

Для каждого `placeId` — Place Details (используй `fetchPlaceDetails` из
`venue.ts`, не выдумывай свой запрос; `PLACES_API_KEY` берётся из env):

- `businessStatus === "OPERATIONAL"`. Отсутствие поля — не «закрыто», но и не
  подтверждение: помечай INFO и не выдавай за проверку.
- `primaryType` / `types[]` не пересекаются с `BLOCKED_PLACE_TYPES` (АЗС, отели,
  супермаркеты, клиники, банки, спортзалы, автосервисы…).
- Название не ловится `isBlockedVenueName` и не входит в `blockedBrands` из
  expansion-файла.
- Название и адрес из Places совпадают с тем, что в строке. Расхождение — обычно
  переезд или переименование → FIX (обновить по Places).
- Координаты из Places совпадают с `lat`/`lng` в пределах ~100 м.

### C. Гейт качества

- `rating >= MIN_RATING` и `userRatingCount >= MIN_RATING_COUNT`.
- Ниже порога — BLOCKER: такую строку `evaluateInitialVenuePolicy` всё равно
  отбросит, она просто засоряет пул и тратит выборку.
- Отдельно отметь заведения, которые **едва** проходят (например 4.0–4.1 или
  30–40 отзывов) — они пройдут гейт, но по факту рискованны для первого свидания.

### D. Цена

- Категории `cafe`, `coffee_shop`, `restaurant`, `lounge`, `museum` требуют
  **положительного доказательства цены**: `priceLevel` от провайдера или
  канонический ценовой тег оператора (`free` / `inexpensive` / `moderate`).
  Нет доказательства → строка не пройдёт автоназначение (`unknown_price`).
  Это самая частая причина, по которой хорошее место лежит мёртвым грузом.
- `PRICE_LEVEL_EXPENSIVE` / `VERY_EXPENSIVE` в `base` — BLOCKER: либо переносим
  в `premium`, либо убираем. Дорогое место не может быть первым автоназначением.
- `park` — единственная категория, которой коммерческая цена не нужна.

Посчитай и выведи отдельной строкой: **сколько добавленных заведений сейчас
провалят автоназначение только из-за отсутствующей цены.**

### E. Часы работы

- `openingHours` (Places `regularOpeningHours.periods[]`) + `utcOffsetMinutes`
  заполнены, либо `hoursConfidence` = `always_open` / `operator_confirmed`.
  Иначе селектор V2 отбрасывает строку (он, в отличие от легаси-ранкера, требует
  часы явно).
- Прогони `isVenueOpenAt` по **реальной сетке слотов свиданий**: 6 дат, каждые
  30 минут с 13:00 до 19:30 локального времени (PRODUCT_SPEC §3.6). Для каждого
  нового заведения выведи, в скольких из 14 слотов дня оно открыто.
- Заведение, открытое менее чем в ~4 слотах (например, музей до 17:00 или бар с
  18:00), — не ошибка, но INFO: оно будет доступно редко, и это надо учитывать
  при оценке покрытия в шаге 3.

### F. Дубликаты

Против **всего** каталога, не только новых строк:
- одинаковый `placeId`;
- координаты ближе ~50 м при похожем названии;
- одинаковая пара `name` + `address`.

Учти легаси: в проде есть строки с `cityKey = NULL`, продублированные по
университетским доменам. Дубль по `placeId` внутри одного домена — FIX; дубль
между доменами — ожидаемое поведение импорта (upsert ключуется по
`universityDomain` + `placeId`), помечай INFO.

### G. География и покрытие

- Координаты внутри города (грубый bounding box достаточно).
- Разложи новые заведения по районам/кластерам (по координатам, кластеризация
  ~2 км). Цель — понять, добавили ли мы **географического** разнообразия или
  снова центр.
- Для каждого кластера посчитай, сколько заведений в радиусе
  `CURATED_VENUE_MAX_COMMUTE_KM` от его центра. Кластер с 1–2 заведениями — это
  будущий «одно и то же место» для всех пар оттуда.

### H. Вайб-разметка (главное, ради чего аудит)

Словари — только канонические, из `packages/shared/src/venue-intent.ts`.

1. **`hardCapabilities` — форматы.** Выводятся детерминированно из категории
   (park → `outdoor` + `walking`; museum → `indoor` + `walking`; остальные →
   `indoor` + `seated`). Никакого LLM: это питает жёсткий фильтр `setting`.
2. **`facetTags` — ambience** (`quiet`, `cozy_public`, `lively`,
   `design_forward`, `scenic`, `romantic_public`). Мягкий сигнал ранжирования,
   0–3 метки. Ставится по имени/типу/цене/рейтингу/операторским `vibeTags`.
   **Нет уверенности — пустой массив, не догадка.** Есть готовый инструмент:
   `pnpm backfill-venue-facets --in=<файл>` (dry-run по умолчанию).
3. **`vibeTags`** — свободные операторские теги (`wine`, `books`, `bakery`,
   `scenic`…). Сохраняй, они самые описательные. Отметь в отчёте, что селектор
   V2 их **сейчас не читает** — это вход в план по алгоритму, а не повод их
   выбрасывать.
4. **Диетические / `alcohol_free` / `step_free`.** Сейчас в каталоге таких
   меток **ноль**, а `satisfiesVenueHardConstraints` требует явного
   подтверждения — то есть любой пользователь, отметивший в Must-haves веган /
   без алкоголя / безбарьерный доступ, гарантированно получает `no_candidates`.
   **Не проставляй их по догадке** — это гейт доступности, ему нужны реальные
   доказательства (сайт заведения, меню, подтверждение оператора). Вместо этого:
   выведи список заведений, для которых доказательство реально достижимо, и
   отдельным пунктом зафиксируй проблему как продуктовую.

Отчитайся числами: сколько новых строк получили ≥1 ambience-метку, сколько
остались пустыми, и какое распределение по шести ambience получилось.

### I. Пригодность для первого свидания (смысловая, не формальная)

Формально пройденный гейт ≠ хорошее место. Отметь INFO:
- шумные/громкие места, где невозможен разговор;
- фастфуд и сетевые точки без «повода прийти»;
- места без сидячих мест там, где формат заявлен `seated`;
- заведения с явно вечерним/алкогольным профилем в дневных слотах;
- всё, что читается как небезопасное или неуютное для женщины вечером — это
  прямо рифмуется с pre-date safety brief.

### J. Итоговая матрица покрытия

Собери таблицу «кластер × категория × ambience» по **всему** каталогу города
после добавления. Именно она отвечает на вопрос, ради которого расширяли базу:

- есть ли в каждом кластере хотя бы 5–8 проходящих гейт заведений;
- для каждой из 6 ambience — сколько мест её реально несут (`romantic_public` и
  `lively` исторически самые пустые);
- для каждой из 6 категорий — сколько мест доступно в вечерних слотах.

Пустые клетки = места, где алгоритм снова будет вынужден повторяться. Это
приоритетный список для следующего расширения.

## Правила

- **Ничего не выдумывать.** Каждое значение — из Places, из файла каталога или
  от оператора. Нет данных → «неизвестно», а не правдоподобное значение.
- **Fail closed.** Сомнение по жёсткому гейту (часы, доступность, цена) трактуй
  как «не проходит», а не «наверное, ок».
- **Ничего не писать без подтверждения.** Сначала dry-run и отчёт. Правки в
  JSON — только после «да». В прод-БД — только по отдельной явной команде.
- **Не менять код** в рамках аудита. Найденные проблемы кода — в раздел
  расхождений, чинить их отдельной задачей.
- Никаких секретов в выводе. Ключи берутся из env, в отчёт не попадают.

## Команды пайплайна

```sh
# 1. Обновить метаданные Places для ревью-списка и сверить с approved-каталогом
pnpm sync-venues:kyiv            # dry-run
pnpm sync-venues:kyiv --apply
pnpm sync-venues:kyiv --check

# 2. Разметить ambience/форматы (LLM для ambience, категория для форматов)
pnpm backfill-venue-facets --in=scripts/curated-venues.kyiv.approved.json
pnpm backfill-venue-facets --in=scripts/curated-venues.kyiv.approved.json --apply

# 3. Импорт в БД (upsert по universityDomain + placeId)
pnpm seed-venues:import --in=scripts/curated-venues.kyiv.approved.json           # dry-run
pnpm seed-venues:import --in=scripts/curated-venues.kyiv.approved.json --apply

# Новые кандидаты из Places под тем же продакшн-гейтом
pnpm seed-venues:pull --config=scripts/curated-venues.config.json
```

Dev-БД поднимается через `pnpm dev:db:up`; аудит по умолчанию идёт против неё.
Прод — только по явному указанию оператора.
